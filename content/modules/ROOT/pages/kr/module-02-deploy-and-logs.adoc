= 데모 앱 배포 및 사용

이 모듈에서는 *{demo-app-name}* 애플리케이션을 클러스터에 배포하고, 이후 모듈의 관측성 실습을 위한 트래픽을 생성합니다.

이 모듈은 두 파트로 구성됩니다:

* *Part A* -- 데모 앱 배포 (백엔드, 프론트엔드, 데이터베이스, MLflow 연동)
* *Part B* -- 애플리케이션을 사용하여 샘플 트래픽 생성

== Part A: 데모 앱 배포

{demo-app-name}은 다음으로 구성된 풀스택 AI 애플리케이션입니다:

[cols="1,2",options="header"]
|===
| 컴포넌트 | 용도

| *planner-backend*
| LLM 연동 및 MLflow 트레이싱이 포함된 FastAPI 서비스

| *planner-frontend*
| React 기반 웹 UI

| *PostgreSQL*
| 공유 데이터베이스 (`redhat-ods-applications` 네임스페이스의 기존 인스턴스 재사용)

| *MLflow*
| 실험 추적 및 트레이스 수집 (설정 스크립트로 사전 배포됨)
|===

=== 단계 2.1: Web Terminal 열기

. *OpenShift Console* 탭을 사용하여 (또는 {productname-short} 대시보드 우측 상단 격자 아이콘을 통해) *{ocp-short} Console*에 접속합니다.
. {ocp-short} Console 우측 상단의 *>_* 아이콘을 클릭하여 Web Terminal을 엽니다.

image::img-initiate-cli.png[OpenShift Console에서 Web Terminal 열기]

`oc`, `git` 등 일반적인 CLI 도구가 사전 설치된 브라우저 내 터미널을 사용할 수 있습니다.

=== 단계 2.2: 환경 변수 설정

배포 스크립트는 세 가지 매개변수가 필요합니다: LLM 기본 URL, API 키, 모델 이름. 강사가 이 값을 제공하거나, 이전 실습의 연속인 경우 이전에 배포한 모델 엔드포인트와 API 키를 사용하십시오.

[source,sh,role="execute"]
----
export LLM_BASE_URL="https://maas.apps.ocp.xxxxxxxxxxxxxx.opentlc.com"
----

[source,sh,role="execute"]
----
export LLM_API_KEY="<MaaS subscription API key>"
----

[source,sh,role="execute"]
----
export LLM_MODEL="<MaaS model path>"
----

[NOTE]
====
플레이스홀더 값을 실제 클러스터 서브도메인, API 키, 모델 이름으로 교체하십시오. 이 값은 강사가 제공하거나 이전 실습에서 사용한 것을 그대로 사용합니다.

예를 들어, 클러스터 도메인이 `ocp.5sh6j.sandbox1809.opentlc.com`이고, 사용자가 `user01`이며, Gemma 4 E4B 모델을 배포한 경우:

[source,sh]
----
export LLM_BASE_URL="https://maas.apps.ocp.5sh6j.sandbox1809.opentlc.com"
export LLM_API_KEY="sk-oai-<your-api-key>"
export LLM_MODEL="publishers/user01/models/redhataigemma-4-e4b-it"
----
====

=== 단계 2.3: 배포 스크립트 실행

배포 스크립트는 완전 자체 포함형으로, git clone이 필요하지 않습니다. 다음 네 단계를 자동으로 수행합니다:

. *PostgreSQL* -- 기존 PostgreSQL 인스턴스를 확인하고 애플리케이션 데이터베이스를 생성합니다
. *설정* -- LLM 및 데이터베이스 연결 정보가 포함된 ConfigMap과 Secret을 생성합니다
. *백엔드 + 프론트엔드* -- 애플리케이션 Pod, Service, Route를 배포합니다
. *마이그레이션 + RBAC* -- 데이터베이스 마이그레이션을 실행하고 MLflow 접근을 구성합니다

다음 명령어로 실행합니다:

[source,sh,role="execute"]
----
curl -sL https://raw.githubusercontent.com/hyogrin/rhoai-basic-agentops-workshop/main/scripts/deploy_demo_app.sh \
  | bash -s -- "$LLM_BASE_URL" "$LLM_API_KEY" "$LLM_MODEL"
----

[TIP]
====
기본적으로 스크립트는 `demo` 네임스페이스에 배포합니다. 다른 네임스페이스를 사용하려면 `--namespace=<NS>`를 추가하십시오:

[source,sh]
----
curl -sL https://raw.githubusercontent.com/hyogrin/rhoai-basic-agentops-workshop/main/scripts/deploy_demo_app.sh \
  | bash -s -- "$LLM_BASE_URL" "$LLM_API_KEY" "$LLM_MODEL" --namespace=user-XX
----
====

=== 단계 2.4: 배포 확인

스크립트가 완료될 때까지 기다립니다. 다음과 유사한 출력이 표시됩니다:

[source,text]
----
  Backend   : https://inference-planner-api.apps.<cluster-domain>
  Frontend  : https://inference-planner.apps.<cluster-domain>
  MLflow    : enabled (experiment: inference-design-planner)
  Database  : inference_planner@postgres.redhat-ods-applications.svc.cluster.local (reused)
----

image::img-deploy-script-output.png[배포 스크립트 성공 출력]


모든 Pod가 실행 중인지 확인합니다:

[source,sh,role="execute"]
----
oc get pods -n demo
----

세 개의 Pod가 표시되어야 합니다:

[source,text]
----
NAME                                  READY   STATUS      RESTARTS   AGE
planner-backend-xxxxxxxxx-xxxxx      1/1     Running     0          2m
planner-db-migrate-xxxxx             0/1     Completed   0          3m
planner-frontend-xxxxxxxxx-xxxxx     1/1     Running     0          2m
----

// TODO: img-pods-running.png를 위 3개 Pod만 표시하는 깨끗한 스크린샷으로 교체
image::img-pods-running.png[demo 네임스페이스에서 실행 중인 Pod]

* `planner-backend`와 `planner-frontend`는 `Running` 상태에 `1/1` ready여야 합니다.
* `planner-db-migrate`는 일회성 데이터베이스 마이그레이션 Job으로, `Completed` 상태에 `0/1`이 정상입니다.
* 네임스페이스에 별도 배포(모델 서빙, 다른 데모)의 Pod가 있을 수 있으나, 이 워크숍과는 무관합니다.

Pod 중 `CrashLoopBackOff` 또는 `Error` 상태가 있다면, Pod 이벤트를 확인하십시오:

[source,sh,role="execute"]
----
oc describe pod <pod-name> -n demo
----

== Part B: 애플리케이션 사용

=== 단계 2.6: 애플리케이션 소개

기업이 LLM을 도입할 때 가장 흔히 직면하는 질문 중 하나는 _"어떤 GPU가 필요하고, 몇 개 필요하며, 이 모델의 서빙을 어떻게 구성해야 하는가?"_ 입니다. 이를 잘못 판단하면 하드웨어에 과도한 비용을 지출하거나 지연 시간 요구 사항을 충족하지 못하게 됩니다. 대부분의 팀은 모델 카드를 수동으로 읽고, VRAM 요구 사항을 교차 참조하며, 배포 매개변수를 추측하는 것에서 시작합니다.

*{demo-app-name}*은 LLM을 사용하여 이 분석을 자동화합니다. Hugging Face에서 모델 이름을 입력하고, 하드웨어 제약 조건(플랫폼, GPU 유형, 수량, 인터커넥트)을 선택하면, 근거 기반 배포 권장 사항을 생성합니다 -- GPU 선택, 메모리 계산, {ocp-short}용 서빙 구성을 포함합니다.

내부적으로 각 분석은 여러 LLM 호출, 도구 실행, 데이터베이스 쿼리를 트리거합니다 -- AgentOps 관측성이 필요한 전형적인 멀티 스텝 AI 워크플로입니다. 이것이 이 앱을 이상적인 데모 애플리케이션으로 만듭니다: 실무자가 실제로 겪는 문제를 해결하면서, 관측성 기술을 학습하는 데 필요한 풍부한 멀티 스텝 실행 트레이스를 생성합니다.

[NOTE]
====
애플리케이션은 여러 언어(영어, 한국어, 중국어, 일본어)를 지원합니다. 우측 상단의 드롭다운에서 언어를 변경할 수 있습니다.

image::img-change-language.png[영어, 한국어, 중국어, 일본어 옵션이 있는 언어 선택기]
====

=== 단계 2.7: 샘플 트래픽 생성

이 단계에서는 애플리케이션을 사용하여 샘플 트래픽을 생성합니다. 여기서 생성된 로그, MLflow 트레이스, GPU 활동은 모듈 3, 4, 5에서 분석합니다.

*1단계 (5단계 중) -- 모델 및 하드웨어:*

. https://huggingface.co/models[Hugging Face^]에서 용도에 맞는 모델을 검색합니다. 이 예시에서는 https://huggingface.co/Qwen/Qwen3.8-27B[Qwen3.8-27B 모델 페이지^]를 사용합니다. 모델 이름을 복사합니다.
+
image::img-hf-modelname.png[Hugging Face에서 모델 이름 복사]

. {demo-app-name} 랜딩 페이지에서 모델 이름(예: `Qwen/Qwen3.8-27B`)을 *Hugging Face Model ID* 필드에 붙여넣습니다. 현재 하드웨어 구성 또는 계획 중인 구성에 맞는 배포 플랫폼, GPU 유형, GPU 수를 선택한 후 *Start Analysis*를 클릭합니다.
+
image::inference-planner-app/img-sample-traffic-1.png[모델 ID 입력 및 하드웨어 풀 선택]
+
image::inference-planner-app/img-sample-traffic-2.png[GPU 유형, 수량, 인터커넥트 선택]

*2단계 (5단계 중) -- 근거 수집(Evidence Discovery):*

[start=3]
. 애플리케이션이 MCP(Model Context Protocol) 도구를 사용하여 여러 소스에서 배포 근거를 자동으로 수집합니다. 모델 아키텍처 세부 정보, vLLM 서빙 레시피, Red Hat 평가 결과, RHOAI 호환성 데이터, GPU 가격 등을 검색합니다.
+
image::inference-planner-app/img-discovery-1.png[Evidence Discovery -- 여러 소스의 웹 검색 결과]
+
활동 로그에는 수집된 근거 항목, 읽은 페이지, 검증 단계가 표시됩니다. 이것이 모듈 4에서 분석할 풍부한 트레이스를 생성하는 멀티 스텝 AI 오케스트레이션입니다. *Next*를 클릭하여 진행합니다.
+
image::inference-planner-app/img-discovery.png[Evidence Discovery -- 콘텐츠 리서치 및 활동 로그]

*3단계 (5단계 중) -- 준비 상태 확인(Readiness Gate):*

[start=4]
. 이 단계에서는 권장 사항을 생성하기 전에 배포 타당성을 검증합니다 -- 모델이 선택한 GPU 메모리에 적합한지, 하드웨어 구성이 지원되는지, 차단 요소가 있는지 확인합니다. *Next*를 클릭하여 진행합니다.

*4단계 (5단계 중) -- 워크로드 프로파일:*

[start=5]
. 의도하는 사용 패턴(예: Chatbot, RAG, Coding Assistant, Agentic, Batch)을 선택합니다. 복수 선택이 가능하며 트래픽 분배를 조정할 수 있습니다. 목표 동시 사용자 수도 지정합니다. *Generate Recommendation*을 클릭합니다.
+
image::inference-planner-app/img-usecase-selection.png[워크로드 프로파일 -- 사용 패턴 선택 및 트래픽 분배]

*5단계 (5단계 중) -- 권장 사항:*

[start=6]
. 제공된 모델 엔드포인트를 사용하여 애플리케이션이 포괄적인 배포 분석을 생성합니다. 권장 사항 페이지에는 다음이 포함됩니다:
+
--
* *모델 개요 및 수집된 근거* -- 모델 아키텍처, 파라미터 수, Discovery 단계에서 수집된 33개 근거 항목 요약.
* *배포, 메모리, 비용* -- GPU 선택, VRAM 활용 내역(모델 가중치, KV 캐시, 오버헤드), 예상 월간 TCO.

image::inference-planner-app/img-reco-1.png[권장 사항 -- 모델 개요, 배포, 메모리, 비용 분석]

* *성능 예측* -- 이론적 처리량, 예상 TPOT 및 TTFT, 배치 크기별 처리량 차트, 계산 방법 분석(메모리 대역폭 바운드, 루프라인 모델, 컴퓨트 바운드 분석).

image::inference-planner-app/img-reco-2.png[권장 사항 -- 성능 예측 및 계산 방법]

* *추론 설계 제안* -- 아키텍처 방향, 핵심 고려 사항, 위험 요소, 대안.

image::inference-planner-app/img-reco-3.png[권장 사항 -- 위험 요소와 대안을 포함한 추론 설계 제안]
--

. 다양한 모델이나 GPU 구성으로 여러 분석을 실행하여 비교할 수 있습니다. 비교하려면 *Saved Recommendations*를 클릭하고, 두 결과를 선택한 후 *Compare*를 클릭합니다. 배포, 메모리, 비용, 성능 필드에서 차이점이 강조 표시된 나란히 비교가 표시됩니다.
+
image::inference-planner-app/img-compare.png[차이점이 강조 표시된 나란히 비교]
+
각 실행은 이후 모듈의 관측성 실습을 위한 추가 트레이스를 생성합니다.
