[#deploy-and-use]
= Deploy and Use the Demo App

In this module you will deploy the *{demo-app-name}* application into your cluster and use it to generate traffic for the observability exercises in later modules.

The module has two parts:

* *Part A* -- Deploy the demo app (backend, frontend, database, and MLflow integration)
* *Part B* -- Use the application to generate sample traffic

== Part A: Deploy the Demo App

The {demo-app-name} is a full-stack AI application consisting of:

[cols="1,2",options="header"]
|===
| Component | Purpose

| *planner-backend*
| FastAPI service with LLM integration and MLflow tracing

| *planner-frontend*
| React-based web UI

| *PostgreSQL*
| Your own database (`inference_planner_<username>`) on the shared PostgreSQL instance in the `redhat-ods-applications` namespace

| *MLflow*
| Experiment tracking and trace collection (pre-deployed by setup scripts). Your traces are recorded in an MLflow workspace tied to your project.
|===

=== Step 2.1: Open the Web Terminal

. Click the *>_* icon in the top-right masthead of the {ocp-short} Console to open the Web Terminal.

image::img-initiate-cli.png[Opening the Web Terminal in OpenShift Console]

This gives you an in-browser terminal with `oc`, `git`, and common CLI tools pre-installed.

=== Step 2.2: Set Environment Variables

The deployment script requires three parameters: the LLM base URL, an API key, and the model name. Your instructor will provide these values, or if this is a continuation of a previous lab, use the model endpoint and API key from your earlier deployment.

[source,sh,role="execute"]
----
export LLM_BASE_URL="https://maas.apps.ocp.xxxxxxxxxxxxxx.opentlc.com/v1"
----

[source,sh,role="execute"]
----
export LLM_API_KEY="<MaaS subscription API key>"
----

[source,sh,role="execute"]
----
export LLM_MODEL="<MaaS model path>"
----

[NOTE]
====
Replace the placeholder values with your actual cluster subdomain, API key, and model name. These are either provided by your instructor or carried over from your previous lab deployment.

The base URL must end with `/v1` (for example `https://maas.apps.<cluster-domain>/v1`), because the application uses an OpenAI-compatible client that sends requests to `<base URL>/chat/completions`. If you leave it out, the deployment script adds `/v1` for you.

For example, if your cluster domain is `ocp.5sh6j.sandbox1809.opentlc.com`, your user is `user1`, and you deployed the Gemma 4 E4B model:

[source,sh]
----
export LLM_BASE_URL="https://maas.apps.ocp.5sh6j.sandbox1809.opentlc.com/v1"
export LLM_API_KEY="sk-oai-<your-api-key>"
export LLM_MODEL="publishers/user1/models/redhataigemma-4-e4b-it"
----
====

Finally, save your project name in a variable. Each participant has their own project named after their username (e.g. `user1`), and the commands in this workshop use `$NS` to refer to it:

[source,sh,role="execute"]
----
export NS=$(oc whoami | tr '[:upper:]' '[:lower:]')
echo "Your project: $NS"
----

=== Step 2.3: Run the Deployment Script

The deployment script is fully self-contained -- no git clone needed. It detects your project from your login (`oc whoami`) and deploys everything there, so your copy of the application is completely separate from other participants'. It performs six steps automatically:

. *Routes* -- Creates the frontend and backend routes with URLs unique to your project (e.g. `inference-planner-user1.apps...`)
. *PostgreSQL* -- Creates your own database (e.g. `inference_planner_user1`) on the shared PostgreSQL instance
. *Configuration* -- Creates ConfigMaps and Secrets with LLM, database, and MLflow connection details, and configures MLflow access
. *Migration* -- Runs database migrations to create the application tables
. *Backend + Frontend* -- Deploys the application pods and services
. *Verify* -- Waits for the pods to become ready and prints a summary

Run it with a single command:

[source,sh,role="execute"]
----
curl -sL https://raw.githubusercontent.com/hyogrin/rhoai-basic-agentops-workshop/main/scripts/deploy_demo_app.sh \
  | bash -s -- "$LLM_BASE_URL" "$LLM_API_KEY" "$LLM_MODEL"
----

[TIP]
====
The first lines of the output show the user and project the script detected, for example `Namespace : user1 (derived from oc whoami)`. Check that it matches your username before continuing.

The script is safe to re-run: resources that already exist are reused or updated.
====

  ✅ Database  : inference_planner_user1@postgres.redhat-ods-applications.svc.cluster.local

Your output shows your own username in place of `user1`.

== Part B: Use the Application

=== Step 2.6: About the Application

One of the most common questions enterprises face when adopting LLMs is: _"Which GPU do I need, how many, and how should I configure serving for this model?"_ Getting this wrong means either overspending on hardware or failing to meet latency requirements. Most teams start by manually reading model cards, cross-referencing VRAM requirements, and guessing at deployment parameters.

The *{demo-app-name}* addresses this by using an LLM to automate the analysis. You provide a model name from Hugging Face, select your hardware constraints (platform, GPU type, count, interconnect), and the application generates an evidence-backed deployment recommendation -- including GPU selection, memory calculations, and serving configuration for {ocp-short}.

Behind the scenes, each analysis triggers multiple LLM calls, tool invocations, and database queries -- exactly the kind of multi-step AI workflow that requires AgentOps observability. This makes it an ideal demo application: it solves a real problem that practitioners encounter, while generating the rich, multi-step execution traces needed to learn observability techniques.

[NOTE]
====
The application supports multiple languages (English, Korean, Chinese, Japanese). You can switch languages using the dropdown in the top-right corner.

image::img-change-language.png[Language selector showing English, Korean, Chinese, and Japanese options]
====

=== Step 2.7: Generate Sample Traffic

In this step you will run through the application to generate sample traffic. The logs, MLflow traces, and GPU activity produced here are what you will inspect in Modules 3, 4, and 5.

*Step 1 of 5 -- Model & Hardware:*

. Search for a model you are considering for a use case on https://huggingface.co/models[Hugging Face^]. For this example, we will use the https://huggingface.co/Qwen/Qwen3.8-27B[Qwen3.8-27B model page^]. Copy the model name.
+
image::img-hf-modelname.png[Copying the model name from Hugging Face]

. On the {demo-app-name} landing page, paste the model name (e.g., `Qwen/Qwen3.8-27B`) into the *Hugging Face Model ID* field. Select a deployment platform, GPU type, and number of GPUs that match your current hardware setup or an envisioned one, then click *Start Analysis*.
+
image::inference-planner-app/img-sample-traffic-1.png[Filling in model identity and selecting hardware pool]
+
image::inference-planner-app/img-sample-traffic-2.png[Selecting GPU type, count, and interconnect]

*Step 2 of 5 -- Evidence Discovery:*

[start=3]
. The application gathers deployment evidence from multiple sources using MCP (Model Context Protocol) tools behind the scenes. It searches for model architecture details, vLLM serving recipes, Red Hat evaluation results, RHOAI compatibility data, and GPU pricing -- all automatically.
+
image::inference-planner-app/img-discovery-1.png[Evidence Discovery -- web search results from multiple sources]
+
The activity log shows the evidence items collected, pages read, and validation steps performed. This is the multi-step AI orchestration that generates the rich traces you will inspect in Module 4. Click *Next* to proceed.
+
image::inference-planner-app/img-discovery.png[Evidence Discovery -- content research and activity log]

*Step 3 of 5 -- Readiness Gate:*

[start=4]
. This step validates deployment feasibility before generating a recommendation -- checking whether the model fits within the selected GPU memory, whether the hardware configuration is supported, and whether any blockers exist. Click *Next* to proceed.

*Step 4 of 5 -- Workload Profile:*

[start=5]
. Select the use case pattern you have in mind (e.g., Chatbot, RAG, Coding Assistant, Agentic, Batch). You can multi-select and adjust the traffic distribution between them. Also specify your target number of concurrent end users. Click *Generate Recommendation*.
+
image::inference-planner-app/img-usecase-selection.png[Workload Profile -- selecting use case patterns and traffic distribution]

*Step 5 of 5 -- Recommendation:*

[start=6]
. Using the model endpoint you provided, the application generates a comprehensive deployment analysis. The recommendation page includes:
+
--
* *Model Overview and Collected Evidence* -- a summary of the model architecture, parameters, and the 33 evidence items gathered during discovery.
* *Deployment, Memory, and Cost* -- GPU selection, VRAM utilisation breakdown (model weights, KV cache, overhead), and estimated monthly TCO.

image::inference-planner-app/img-reco-1.png[Recommendation -- model overview, deployment, memory, and cost analysis]

* *Performance Forecast* -- theoretical throughput, estimated TPOT and TTFT, throughput vs batch size chart, and the calculation method breakdown (memory-bandwidth bound, roofline model, compute-bound analysis).

image::inference-planner-app/img-reco-2.png[Recommendation -- performance forecast and calculation method]

* *Inference Design Suggestion* -- architecture direction, key considerations, risk factors, and alternative approaches.

image::inference-planner-app/img-reco-3.png[Recommendation -- inference design suggestion with risk factors and alternatives]
--

. You may try running multiple analyses with different models or GPU configurations for comparison. To compare, click *Saved Recommendations*, select two results, then click *Compare*. The application displays a side-by-side comparison with differences highlighted across deployment, memory, cost, and performance fields.
+
image::inference-planner-app/img-compare.png[Side-by-side comparison with highlighted differences]
+
Each run generates additional traces for the observability exercises in the following modules.
